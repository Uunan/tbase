# TamgaBase S3 Storage Backend

TamgaBase v1.3+ ships with two storage backends behind the same `StorageBackend` interface:

```
StorageBackend
    ├── LocalStorageBackend   (default)
    └── S3StorageBackend      (AWS S3)
```

## 1. Why S3
- Durable, managed object storage with 11 nines durability.
- The S3 backend mirrors the local backend layout exactly, so behavior is identical:
  CAS deduplication, snapshots, cluster metadata, quota, isolation, key rotation.
- Single-part `PutObject`/`GetObject` are atomic: interrupted uploads never leave partial objects.

## 2. Enabling S3

```bash
# 1) Set credentials in the environment (NEVER in config.json or source code)
export AWS_ACCESS_KEY_ID=AKIA...
export AWS_SECRET_ACCESS_KEY=...
export AWS_REGION=eu-north-1
export AWS_S3_BUCKET=my-bucket
export TAMGABASE_S3_PREFIX=tamgabase        # optional; isolates this server's keys

# 2) Tell TamgaBase to use S3 (server mode)
tamgabase storage s3
#   → prompts for bucket, region, optional prefix
#   → writes only storageBackend/s3Bucket/s3Region/s3Prefix to config.json

# 3) Start the server
tamgabase server
```

Switch back at any time with:

```bash
tamgabase storage local
```

`local` remains the default and its behavior is unchanged.

## 3. Configuration Reference

| Setting | Where | Example |
|---------|-------|---------|
| `storageBackend` | `config.json` (via `tamgabase storage ...`) | `"s3"` / `"local"` |
| `AWS_ACCESS_KEY_ID` | environment only | — |
| `AWS_SECRET_ACCESS_KEY` | environment only | — |
| `AWS_REGION` / `AWS_DEFAULT_REGION` | env, or `config.json` via `storage s3` | `eu-north-1` |
| `AWS_S3_BUCKET` | env, or `config.json` via `storage s3` | `my-bucket` |
| `TAMGABASE_S3_PREFIX` | env, or `config.json` via `storage s3` | `tamgabase` |

Precedence: environment variable wins over `config.json`.

## 4. Object Layout on S3

| Content | Key pattern |
|---------|-------------|
| CAS objects | `<prefix>/objects/<first_2_hex>/<remaining_62_hex>` |
| Cluster configs | `<prefix>/metadata/cluster_config_<clusterId>.json` |
| Token index | `<prefix>/metadata/cluster_token_index.json` |
| Snapshots | `<prefix>/metadata/cluster_<clusterId>_<snapshotId>.json` |
| Latest pointer | `<prefix>/metadata/cluster_<clusterId>_latest.json` |

Deduplication is global: identical content always maps to one object, regardless of cluster.

## 5. Security
- Credentials are read from the environment only; they never appear in `config.json`, snapshots, logs,
  API responses, or error messages.
- The backend addresses only the configured bucket — no `ListBuckets`, no other AWS APIs.
- Minimum IAM permissions (see `docs/SECURITY.md` section 6).
- All AWS errors are mapped to generic `S3: ...` messages before reaching the API layer.
- `SlowDown` (503) is retried with backoff.

## 6. Failure Modes (verified in production E2E tests)

| Scenario | Result |
|----------|--------|
| Invalid credentials | `S3: invalid AWS credentials` — server healthy |
| Wrong bucket | `S3: bucket/object not found (NoSuchBucket)` — server healthy |
| Wrong region | `S3: wrong region configured for this bucket` — server healthy |
| Network error / DNS failure | `S3: network error connecting to AWS` — server healthy |
| S3 outage during request | HTTP `500 {"error":"S3: ..."}` — server stays up, health OK |

## 7. Testing
The E2E suite in `src/e2e/run.ts` exercises the full stack against a real bucket:

```bash
# Full S3 suite (needs AWS_* env vars):
AWS_REGION=eu-north-1 AWS_S3_BUCKET=my-bucket node dist/e2e/run.js --backend s3

# Local regression suite:
node dist/e2e/run.js --backend local
```

Test data is always isolated under an `e2e-test-*` prefix in the bucket and cleaned up afterwards;
the rest of the bucket is never touched.
